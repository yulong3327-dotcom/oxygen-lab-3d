# 3D 化学实验生产与交接规范

从实验材料、步骤和参考图出发，产出可复用的器材、可独立运行的实验配置，以及同一个化学实验室中的项目入口。Blender 用来制作和审看仪器，Three.js 用来呈现网页交互；Agent 和 MCP 只参与制作和检查，不是学生端依赖。

## 开工与接续

在本仓库根目录使用 Node.js 22 或更新版本。替换示例 ID；项目已存在时，跳过 `init`。

```powershell
npm ci
npm run lab -- init example-lab
npm run lab -- list-assets
```

填好配置后，运行以下命令：

```powershell
npm run lab -- validate example-lab
npm run dev
```

打开 `experiments/<id>/intake.md`、`experiment.json` 和 `review.json`，确认上次停在哪一轮，继续校验和修改。新建的配置是草稿，按 [配置与资产字段约定](CONFIG.md) 填写标题、器材和步骤。按服务器输出的 HTTP 地址打开 `/platform/player.html?id=<id>` 预览草稿，发布平台入口是 `/platform/`；现有制氧独立入口仍是根目录 `index.html`。新实验涉及 GLB 和模块加载，用 HTTP 预览。

接收材料时整理：实验标题和教学目标、器材清单和数量、参考视图或形状/尺寸要求、正确操作顺序、每步触发和可观察现象、预计错误操作及反馈、需要保留或排除的内容、交付对象。标明每条事实来自哪里，哪些是待确认。参考图登记用途、权属和涉及的资产；未获公开许可的图、课件和评审材料放仓库外，或放在 Git 已忽略的 `experiments/<id>/references/`、`experiments/<id>/evidence/`，确认这些内容没有被打包进模型、截图或公开分支。素材缺失时可先做资产盘点和独立的预览准备；不要把推测写成教材事实。

## 器材库与实验配置

| 文件或目录 | 用途 |
| --- | --- |
| `assets/catalog.json` | 共用目录：查询器材 ID、模型版次和实际可用文件。 |
| `assets/<id>/v<version>/` | 版本化的器材交付。Blender 资产在版本目录内保留可编辑源文件和网页 GLB，并按库中同类器材的约定声明连接点。 |
| `experiments/<id>/intake.md` | 教学目标、材料索引、器材复用判断、步骤和交接事项。 |
| `experiments/<id>/experiment.json` | 实验播放器读到的配置，引用器材 ID 和版本，描述实验步骤。 |
| `experiments/<id>/review.json` | 按指纹保留模型、网页和教学评审记录；提交前检查是否含私有信息。 |
| `platform/catalog.json` | 公开平台项目列表。草稿先单独预览，确认后才列入。现有实验保留已上线入口。 |

在定制前按器材的功能和连接形式查库。每项登记为**复用确定版本、从旧版派生新版、或新建**；已有器材外观、尺寸和装配点能满足要求时优先复用。候选器材只进入预览，确认过的版本才能作为后续实验的正式复用依据。还没转换成 Blender/GLB 的制氧程序化器材不当作已经交付的模型源文件。不能直接把网页或 `lab.js` 当 Blender 资产打开；可用版本相容的 Three.js 导出器提取所选静态网格作为底稿，并在 Blender 中复核比例、原点、轴向和玻璃材质。

器材 ID 是稳定名称，`version` 是和它组合使用的整数版次。从已有器材改出新版时，沿用 ID、新增版本目录，不覆盖旧版。新建模型以 `candidate` 入库，先在本地预览；该版模型得到实际确认后才能标为 `approved`，供正式项目引用。交付允许公开的 `.blend`、`.glb` 和一张辨认外形的预览图，记录尺寸、朝向、原点和来源。Blender 用公制、单位缩放 1（米），把可导出的网格和锚点放进 `ASSET` 集合；相机和灯放在集合外。目录中的 `anchors` 用导出后 GLB 坐标（Y 轴向上）记录原点、夹持点等实际需要的坐标。吸附、玻璃/液体叠层、水位、气泡、状态和反馈等实时能力由网页按课程需求实现，Blender 网格提供外形和必要的节点。

用当前 Blender 可执行文件导出；若 `blender` 不在 PATH，将首个命令词换成已核实的可执行文件路径（PowerShell 对带空格的路径用 `& '绝对路径'`）。下例路径用来说明参数；日常制作替换为当前器材和版本。不要无意覆盖已发布的版本。

```powershell
blender --background assets/stand/v1/stand.blend --python-exit-code 1 --python tools/blender/export_asset.py -- --output assets/stand/v1/stand.glb
```

## 分工、评审与发布

| 环节 | 负责人 | 交付和检查 |
| --- | --- | --- |
| 立项 | 主 Agent、教学 Agent | 把用户材料整理成器材清单、课程步骤和验收用例，列出影响建模或教学的缺口；同步可独立完成的工作。 |
| 查库与 Blender 制作 | 建模 Agent | 按实验清单给出复用表；把新增/修改器材做成独立版本。给用户可打开的 Blender 文件、关键角度或装配图、版本和本轮变更。 |
| Blender 确认 | 用户或明确指定的评审人 | 对该版外形、相对比例、连接处与参考图确认或留言。按意见修订并再次提交；只复用已审版本的项目可明确记录沿用的证据。 |
| 网页预览 | 前端 Agent | 用选定 ID 的资产和共用动作对接步骤。每步清楚说明起始状态、可操作对象、触发条件、预期现象、错误反馈和重置结果。能力缺失时先添加可独立测试的通用能力；不以复制旧实验规避。 |
| 网页和教学确认 | 验收 Agent、用户或指定教师 | 交付实际预览地址、关键步骤截图和桌面/手机测试结果；请评审人检查交互、教学表述、实验顺序与现象。意见进入下一轮，实质改动后重跑受影响路径。 |
| 纳入平台 | 主 Agent | 当前版本的模型、网页和教学评审完成、自动校验通过且获得发布授权后，才登记到 `platform/catalog.json`。运行 `npm run check` 和 `npm run build`，用 `npm run lab -- serve 8001 --dist` 验证构建产物。只发布 `dist/`，不使用仓库外的旧版发布脚本上传整个源码或草稿；上线后复核入口、项目地址和旧实验可访问。 |

主 Agent 负责分配清晰的文件范围，汇总检查结果。已有资产审查和教学拆步骤可并行；确认了装配点后，建模和网页原型可并行；最终用双方已确认的版本做集成验收。同一个 `.blend` 不做多人同时编辑。开始集成之前，记录资产版本及网页配置版本，不用运行时“最新”替代。

提交每轮预览前，计算对应内容的指纹，将该指纹连同可核对的预览交给实际评审人：

```powershell
npm run lab -- fingerprints example-lab
```

`model` 指纹绑定选用器材的目录元数据（审核标记除外）、源模型、GLB 和预览图；`web` 指纹包含模型指纹、实验配置和共用网页文件；`teaching` 指纹在网页指纹的基础上绑定 `intake.md`。把实际意见追加到 `review.json` 的对应数组，填写 `fingerprint`（原样复制对应指纹）、`decision`（`changes-requested` 或 `approved`）、`reviewer`、`date` 和 `notes`。勾选测试项不能代替用户确认。等待意见时保留待审；先在 `intake.md` 说明已交付的预览和下个动作，再生成教学评审指纹。收到修改意见后修订和重跑受影响的检查，再用新指纹提出评审。备注记录实际查验的文件或地址；私有证据在本地用不泄露内容的编号关联。只有取得对应的真实确认，才能把项目标成已评审。

## 工具选择与验收

- **Blender**：先实际打开 `.blend` 检查；导出后用浏览器复核单位、物体位置、玻璃前后关系和命名节点。重复导出采用已检查的 Blender 后台脚本和工具版本；由目录中的资产格式决定参数。仅有命令行导出成功不能替代看模型。
- **MCP（可选）**：本仓库的 MCP 由客户端在仓库根目录启动 `node scripts/lab-mcp.mjs`，用 stdio 连接。它提供只读操作 `list_assets`、`validate_experiment` 和 `review_fingerprints`，预览服务器另行启动。现有浏览器工具或 Playwright MCP 用于操作预览、抓取截图、查控制台；无 MCP 时用相同 CLI 和浏览器完成。记录实际用了哪个工具。
- **Blender 联调**：安装 [MCP for Blender](https://github.com/ahujasid/mcp-for-blender) 后，在 Blender 打开当前候选 `.blend`，鼠标放在 3D 视图，按 `N`，进入 **MCP for Blender → Connect to MCP server**。Codex 中使用 `blender` 服务，先调用 `get_scene_info` 核对连接的是本轮要处理的场景，再做调整。只在本机用 `127.0.0.1:9876`，不启用远程访问和遥测；联调完成后可在同一面板断开。Blender 或 Codex 已打开的旧会话可能需要重新打开才能读取新配置。正式导出仍使用上面的 Blender 后台脚本。
- **固定校验**：运行 `npm run lab -- validate <id>` 检查单个项目，`npm run check` 检查目录及所有配置，再按实验用例实际验证。需要新通用动作或引擎行为时，要有可重复运行的回归检查。将同一版本的检查结果写进交接。
- **网页最低验收**：从平台或草稿地址打开，资产成功加载；桌面拖拽/点选和窄屏触控能完成正确路径；错序、错放不会误推进，提示可见；每步现象和完成状态符合教学记录；重开和重置回到预期状态；检查浏览器运行错误和已有项目的关键路径。含玻璃和液体的步骤还要用不同视角检查。

每次交接至少给出项目 ID、当前阶段、所用资产 ID/版本、预览地址、两轮评审状态、已实际执行的检查、未决事项和下一个可执行动作。后续 Agent 可从仓库文件恢复，不需要重新询问已经确认过的信息；对仅存在于往期对话而未存档的“确认”，先核对证据。

工作流可复用的验收标准：用不同于第一课的实验验证器材和通用动作都能跨课复用；当所需能力都已存在时，下一位 Agent 只新增项目配置和验收数据，就能得到新的预览。目录能列出已有项目与新项目，独立验收新项目的同时回归旧项目。

## GitHub Pages 正式发布

部署前，仓库管理员需在 GitHub 仓库的 **Settings → Pages → Build and deployment → Source** 选择 **GitHub Actions**。落实发布授权后，从默认分支手动运行 [Deploy lab to GitHub Pages](../.github/workflows/pages.yml)。工作流先校验和构建，再上传并部署 `dist/`；提交源码或推送分支不会自动触发它。正式构建不包含草稿实验、候选器材、Blender 源文件、原始参考图或评审记录。不要使用旧版上传整个源码树的发布脚本。
